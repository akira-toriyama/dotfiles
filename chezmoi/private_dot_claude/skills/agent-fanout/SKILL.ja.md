# Fan-out: 支出は変更に見合うこと

品質優先は変わらない。物差しはユーザーのもの（2026-11-15）: 修正の中身で説明できる
トークン消費は問題ない。説明できない消費はプロセスの欠陥で、答えは微調整ではなく
再設計（「小手先の対応は不要」）。

## agent のコスト

毎ターン、context 全体を読み直す。したがって agent のコストは **context × turns** で、
走る長さの 2 乗で増える。出力と thinking は全体量の 1% 未満。

この skill が生まれる元になった失敗での実測（glyph e-b76m、1 日、23 transcript、
`claude-agent-usage`）:

| 項目 | 実測 |
|---|---|
| その日に読んだ token | 413M（出力: 2M） |
| workflow agent の平均（18 体） | 158k context × 101 turns |
| 最悪の agent | 432k context × 199 turns = 58M、fix 1 ラウンド |
| main loop 自身 | 208 turns、48M: 2 番目に高い行 |
| fix 1 ラウンド | 変更 250〜500 行に対して 10M〜20M を読む |
| 長いコマンドの待ち | 全読み込みの 15%。fixer では 18〜30% |
| host | 12 コアに重い agent 5〜6 体、load 50〜94、gate が 2〜3 倍遅い |

ユーザーが支出を異常だと言うまで、agent ごとの数字を誰も見ていなかった。

## fan-out の前

1. 見積もりを quota 行の隣に書く: agent 数 × ラウンド数 × 各 agent が達すると見込む
   サイズ、そしてそれで買う変更のサイズ。agent が最後のターンまでに何を読んでいるかを
   言えないなら、切り方は設計されていない。
2. 小さい context と短い実行になるよう切る:
   - agent 1 体に関心事 1 つ、入力は狭く: ファイルと所見を、パスと行範囲で渡す。
     「設計文書を全文読め」とは決してしない。
   - 長い出力はファイルへ書き、`pare` を通して戻す。
   - agent は長いコマンドを走らせて待たない。フルの gate、フルのテストマトリクス、CI を
     agent の中から poll しない。agent は push して戻り、CI が gate を 1 回走らせ、
     main loop が判定を読む（`cifail wait`）。agent が走らせるのは、自分が触った範囲に
     絞ったチェックだけ。
   - ラウンドは新しい agent であり、セットアップ全体をもう一度払う。main loop は次の
     ラウンドを起動する前に、そのラウンドの所見と使用量を読む。自分で再起動するループは
     各ラウンドの値段を隠す。
3. main loop をデータの通り道に置かない: 結果はファイルへ。main loop が読むのは判定と
   数字で、レポート全文ではない。
4. 同時に走らせる重い agent は、host が gate を遅くせずに運べる数だけにする。遅い gate は
   すべての agent を長くする。

## 最初のユニットの後

`claude-agent-usage`（引数なし: この project の最新セッション）を実行し、その行を、
そのユニットが変えたものの `git diff --shortstat` の隣に並べる。両方をユーザーに
それぞれ 1 行で報告する。変更が支出を説明しないなら、そこで fan-out を止めて切り方を
再設計する。「平均すれば釣り合うか見る」ために残りのユニットを起動しない。
