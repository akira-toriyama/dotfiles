# Fan-out: 支出は変更に見合うこと

品質優先は変わらない。物差しはユーザーのもの（2026-11-15）: 修正の中身で説明できる
トークン消費は問題ない。説明できない消費はプロセスの欠陥で、答えは微調整ではなく
再設計（「小手先の対応は不要」）。

## agent のコスト

毎ターン、context 全体を読み直す。したがって agent のコストは **context × turns** で、
走る長さの 2 乗で増える。出力と thinking は全体量の 1% 未満。

この skill が生まれる元になった失敗での実測（glyph e-b76m、1 日、23 transcript、
`claude-agent-usage`）:

| 項目 | 実測 |
|---|---|
| その日に読んだ token | 413M（出力: 2M） |
| workflow agent の平均（18 体） | 158k context × 101 turns |
| 最悪の agent | 432k context × 199 turns = 58M、fix 1 ラウンド |
| main loop 自身 | 208 turns、48M: 2 番目に高い行 |
| fix 1 ラウンド | 変更 250〜500 行に対して 10M〜20M を読む |
| 長いコマンドの待ち | 全読み込みの 15%。fixer では 18〜30% |
| host | 12 コアに重い agent 5〜6 体、load 50〜94、gate が 2〜3 倍遅い |

ユーザーが支出を異常だと言うまで、agent ごとの数字を誰も見ていなかった。

## fan-out の前

1. 見積もりを quota 行の隣に書く: agent 数 × ラウンド数 × 各 agent が達すると見込む
   サイズ、そしてそれで買う変更のサイズ。agent が最後のターンまでに何を読んでいるかを
   言えないなら、切り方は設計されていない。
2. 小さい context と短い実行になるよう切る:
   - agent 1 体に関心事 1 つ、入力は狭く: ファイルと所見を、パスと行範囲で渡す。
     「設計文書を全文読め」とは決してしない。
   - 長い出力はファイルへ書き、`pare` を通して戻す。
   - agent は長いコマンドを走らせて待たない。フルの gate、フルのテストマトリクス、CI を
     agent の中から poll しない。agent は push して戻り、CI が gate を 1 回走らせ、
     main loop が判定を読む（`cifail wait`）。agent が走らせるのは、自分が触った範囲に
     絞ったチェックだけ。
   - ラウンドは新しい agent であり、セットアップ全体をもう一度払う。main loop は次の
     ラウンドを起動する前に、そのラウンドの所見と使用量を読む。自分で再起動するループは
     各ラウンドの値段を隠す。
3. main loop をデータの通り道に置かない: 結果はファイルへ。main loop が読むのは判定と
   数字で、レポート全文ではない。
4. 同時に走らせる重い agent は、host が gate を遅くせずに運べる数だけにする。遅い gate は
   すべての agent を長くする。

## 最初のユニットの後

`claude-agent-usage`（引数なし: この project の最新セッション）を実行し、その行を、
そのユニットが変えたものの `git diff --shortstat` の隣に並べる。両方をユーザーに
それぞれ 1 行で報告する。変更が支出を説明しないなら、そこで fan-out を止めて切り方を
再設計する。「平均すれば釣り合うか見る」ために残りのユニットを起動しない。

## 再設計が測ったこと

glyph t-60v9 は上のデータをもとに e-b76m を再設計し、2026-11-23 に 4 ユニット（4 本の
pull request）をそれで回した。切り方:

- 委ねる単位は所見 1 件か作業票 1 枚で、ユニットの 1 ラウンドではない。作業票には
  ファイルと行、裁定、足すテスト、走らせるコマンドを書く。worker は編集し、その
  package のテストと触った mutation の行を走らせ、push して 10 行を返す。予算:
  20〜40 ターン。
- 検査は修正 diff 1 つと、それが答える所見に範囲を絞り、報告者の script を使い回し、
  報告を最後のメッセージとして返す。予算: 40 ターン。再検査は同じ検査役を 3〜12
  ターン resume する。
- フルの gate は CI でだけ走らせる。2 分を超えるコマンドを待つ agent はいない。
  main loop は push ごとに 1 回、背後の wait を通して CI を読む。
- main loop は所見をすべて自分で裁定し（直す、理由を付けて退ける、task にする）、
  次の段を起動する。ひとりでに再起動するものは無い。

| 何 | 旧プロセス | 再設計 |
|---|---|---|
| 1 ユニット、修正 + 検証 1 ラウンド | 読んだ量 38M、agent 2 体 | 5M（パイロット） |
| 4 ユニット、検査 → 修正 → 再検査、PASS まで | 1 日で届かず | 37M、agent 10 体、325 ターン |
| agent 1 体 | 158k の context × 101 ターン | 55k〜227k × 3〜55 ターン |
| main loop | 208 ターンで 48M | 119 ターンで 28M、context は最大 359k |

直らなかったこと、そして数字が次にやれと言っていること:

- いまや main loop が最も高い行だ。最初の検査から最後の land までを最も高いモデルの
  1 セッションで走らせ、agent の報告と CI の要約がすべてその context に残った。
  main loop は段の境目（検査が済んだところ、そして land）で切り、状態は task body に
  置き、複数手順の儀式（land、main の merge、CI 待ち）は script にして、5 ターンかけて
  いたことを 1 ターンで済ませる。
- agent の resume はターン数では安く、1 ターンあたりでは高い。4 回 resume した検査役は
  227k の context で 49 ターン、7.2M を読み、新しく起動したどの agent よりも多かった。
  resume は 2 回までにし、その後は狭い指示で新しい agent を起動する。
- 後追いの修正は 1 ラウンドまるごとかかる: worker、再検査、CI。ここで避けられた
  ラウンドを生んだのは 3 つ: 作業票を越えて guard を足した worker（2 ラウンド）、測定
  なしに網羅を主張した main loop の裁定（1 ラウンド）、worker が走らせなかった
  formatter（CI 1 周）。worker には作業票だけをやってそれ以外はしないよう伝え、修正を
  確かめるラウンドで検査役に裁定の前提を反証させ、formatter を worker の push 前の
  リストに入れる。
- 1 つの共有ファイル（ここでは mutation ledger）に皆が追記する pull request は並列には
  land できない: land のたびに、残りで main の merge と CI 1 周が要った。順に land し、
  pull request 1 本につき CI 1 周を見込む。
