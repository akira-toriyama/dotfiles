# macOS アプリのアーキテクチャ — 家の方法論

ネイティブ macOS アプリ（Swift/AppKit または SwiftUI）を、差し替え可能な OS backend の上で複数の UI サーフェスを駆動する純粋ロジックの core として構造化するための、再利用可能な方法論。実運用の window manager コードベースから蒸留し、型名は一般化、原則は保存した。**適用範囲 = macOS アプリ**（言語横断の汎用ではない）。

## レイヤリングと依存規則

アプリを 3 レイヤーに分割し、*同一の純粋 core が複数の UI サーフェスを駆動* し、*同一の UI が複数の backend の上で走る* ようにする:

- **Core** — 純粋ロジックのみ: ドメイン状態、ルール、エンジン、**port protocol**、イベント型。値レベルの OS プリミティブ（`CGRect` のような幾何型）は可; **UI framework 不可、backend 不可、OS 操作不可**。
- **Adapter** — ちょうど 1 つの OS/framework backend を包み、backend 固有の型が現れてよい **唯一** の場所。adapter は複数あってよい; backend の型がそのモジュールの外へ逃げ出すことは決してない。
- **View** — GUI 専用、薄く保ち、ビジネスロジックを持たない。**port protocol** と話し、具体の adapter とは決して話さない。

依存規則（Clean Architecture / Hexagonal）: **ソースコード上の依存は常に内側**、Core の protocol へ向く。adapter と view は Core に依存し、Core は外側の何にも依存しない。

- **「レイヤーを跨いだら、それは必ず protocol の欠落を意味する。」** 判定法: ある型が境界の向こうへ手を伸ばす必要があるなら、port を導入せよ — 型を漏らすな。
- **継ぎ目で backend 中立なモデル型へ変換せよ。** view と controller が adapter 内部の型を見ることは決してあってはならない。

### なぜ 2 つでなく 3 レイヤーなのか

価値は 3 つの別々の場面で実現する — どれもあり得ないなら 3 つ目のレイヤーは要らないかもしれない; どれか 1 つでもあり得るなら残せ:

1. **テスト面** — Core は UI framework 無しで全面的に動かせる; adapter には作り置きのイベントストリームを流す contract test が当たる; view は薄いままでいる。
2. **backend の差し替え** — 新しい adapter は stub から始まり、どの view も壊さずに段階的に育つ; 古い方の廃止は 1 モジュールの差し替えで済む — *view が port しか知らないから*。
3. **1 つの状態に対する複数の view** — 各 view は同じモデルの一面; 新しい view は Core も Adapter も触らずに挿さる。

## UI ツールキット: 最上位を既定にし、脱出口を封じ込める

**View** レイヤーがどの UI framework を import するかはアーキテクチャ上の選択であり、view ごとの気分ではない。**最上位のツールキット**（macOS では SwiftUI）を既定にし、下位のもの（AppKit）は **小さく名前を与えた必須 floor の集合に封じ込めた脱出口** として扱う — 上位のツールキットが本当に届かない場所のことだ。

**floor の正本リストはここには無い。** 後述の規律に従い、それはプロジェクト自身の正典に属する; この家では共有 UI ライブラリ **[Sill](https://github.com/akira-toriyama/sill)** がそれにあたる — floor を宣言する前にその `Package.swift`（ライブラリ契約）を確認せよ。Sill が既に覆った floor はもう floor ではないからだ。家の既定（SwiftUI + Sill）は `mac-app-dev` skill を見よ。

ある実運用コードベースで観測された floor。**「必須」が何を意味するかの較正としてだけ** ここに置いてある — 写して使うリストではない:

- **IME / テキスト入力コア** — marked-text（変換中）の傍受と、上位のフィールドが公開しない確定前のキー配送（Return / Esc / 矢印）。
- **フォーカスを保つ非アクティブ化パネルの shell** — 最前面アプリ / メニューバーを奪わずに key + 入力を受け取るフローティングウィンドウ（および親をはみ出す popup）。低レベルなのは *shell* だけ; その中身は上位の view をホストする。
- **選択可能なリッチテキスト描画** — 上位のテキストプリミティブでは選択と排他になる、インライン装飾（コード pill、表 / 引用の罫）付きの連続選択 + コピー。

境界を侵食させないための規律:

- **それらの floor の外で低レベルツールキットが必要だと*感じた*ものは、すべて「たぶん上位でもできる」として扱え — 広げる前に spike / MRE で証明せよ。** floor は証拠で増えるのであって、便利さで増えることは決してない。（「レイヤーを跨ぐ ⇒ port の欠落」と同型: 低レベルツールキットに手を伸ばす ⇒ まず上位に道が無いことを証明せよ。）
- **脱出してよいのは *機構* だけで、chrome は決して対象にならない。** floor 扱いのウィジェットでも、色 / フォント / レイアウト / データ / エラー状態は上位のままにする; 低レベル側はこれ以上分解できないエンジン（text view のコア、ウィンドウ shell）であって、それ以上ではない。
- **floor の正本リストは方法論ではなくプロジェクトの正典に置け。** *形* — 少数の必須 floor、広げる前に検証 — は安定している; 正確なリストはプラットフォームと共有 UI ライブラリの進化に伴って動く。UI 移行を追跡している場所に固定し、そこを参照せよ。

## Ports & Adapters

**port** とは、外部能力の 1 つの *軸* を表現する Core 内の protocol（例: backend port = 状態クエリ + 変更コマンド + イベントストリーム; capture / 副次リソース用は別の port）。

- **実装が 1 つでも port は残せ。** 実運用の adapter が 1 つきりでも継ぎ目は元が取れる: 作り置きデータを流す stub/fake に差し替えて純粋な core を単独でテスト可能にする、**テストの継ぎ目** だからだ。
- **port は backend の軸に沿って分割し、恣意的に分けるな。** ある能力が *backend の軸* で異なるとき — 別の OS framework、別の permission/entitlement、あるいは任意 / バージョンで可否が決まる — その能力は専用の port + モジュールに値する。同じ軸 → 同じ adapter。
- **port は framework 中立に保て。** データを運べる範囲で *最も中立な* 表現を返す / 受け取る（UI framework の画像ではなく中立な画像型）; UI framework での包装は view へ押し出し、view モジュールが OS backend を一切 import しないようにする。
- **変わりうる外部契約はすべて port として扱え。** 入力文法（CLI/引数）、ワイヤフォーマット、ディスク上のスナップショット: 生の外部入力 → 安定した内部表現へ写す *純粋な translator* を Core に置き、不純な殻（終了コード、stderr、I/O）は外側のクライアントに留める。「parser が文法に対して持つ関係は、backend port が backend に対して持つ関係と同じ: 外界が変わっても hexagon の内側を安定に保つ継ぎ目である。」構文の移行を跨いでもペイロードはバイト単位で同一のままになる。

## DDD の構成要素

コードがそれらの名前を一度も名乗らなくても、パターンは適用されている。短い **対応表**（Clean-Arch / DDD ↔ 自分のモジュール）を持ち、2 つの語彙がずれないように、また意図が冷えた状態での再オープンを生き延びるようにせよ。

- **Entity** — 同一性を持つ可変のドメインオブジェクト。
- **Value Object** — 不変の identity / スタイル / 幾何の値。
- **Aggregate Root** — 子を *所有する* entity（メンバーを所有するコンテナ）; 子の変更は root 経由で行う。
- **Repository** — port protocol 群。
- **Domain Service** — どの単一 entity にも属さないステートレスな操作（reconciliation、幾何クエリ、フォーカスの強制、スケーリング）。
- **Domain Event** — *async stream 経由で消費される* backend イベント型（「ドメインイベント」節を見よ）。
- **Bounded Context** — 1 バイナリ = 1 コンテキスト; コンテキスト間の翻訳は不要。
- **Ubiquitous language** — 用語は glossary で統治する; 名前の変更はコードと *同一の変更* で入る。

## 何を先送りするか（YAGNI）とその理由

正統な Clean Architecture / MVVM が規定するレイヤーは、意識的に飛ばしてよい — **ただし決定を反転させる構造的トリガーを正確に記録し、それが発火するまで蒸し返すな。**

- **独立した Use Case / Interactor レイヤーは置かない** — use case の形が backend 呼び出し（＋リトライ）を包む 1 行のラッパーである間は。レイヤーにしても 100% boilerplate になる。Controller に畳み込め。**抽出のトリガー:** 新しい view が入り、**かつ** 同じ操作が 2 つ以上の view のコードパスに現れたとき。
- AppKit では **ViewModel を置かない**: 形の良い **view ↔ controller の callback protocol** — 下りは不変スナップショット、上りは意図の callback — が boilerplate 無しで既に ViewModel の仕事をしている。**トリガー:** 1 つの view を複数のウィンドウ / ホストで再利用しなければならなくなったとき。（SwiftUI では損得勘定が違うが、トリガーに基づく推論はそのまま通用する。）
- **一般則:** そのレイヤーの現状のインスタンスが純粋な boilerplate になるなら先送りする; トリガーを正確に名指す（たいていは「同じロジックが今や 2 箇所以上にある」）; 決定を凍結する（「明示的なレビューの回を経ずに蒸し返さない」）。

## 継ぎ目とテスト可能性

- **どのレイヤーに置くかは、テスト可能性も判断材料にせよ。** 純粋な計算 / 純粋なデータのヘルパーは *唯一の呼び出し元が adapter にあっても* Core に属する — 移すことで、テスト不能な OS 結合ユニットが、完全に網羅された純粋ユニットに変わる。
- **port が差し替えの継ぎ目** — stub を port に適合させ、本物の adapter と入れ替えて、作り置きデータで core を駆動する。
- **純粋な値型は最初の利用者と一緒に 1 つの変更で出せ** — 利用者のいない孤児を生む分割はしない — そうすればどの merge も単独でテスト可能かつ意味を持つ。
- **内部構造ではなく振る舞いに対してテストせよ** — 結果の一致 / 描画の冪等性の一致を使い、体裁だけの変更で壊れるソース位置に敏感な比較（例: AST の一致）は使わない。

## ドメインイベント

OS の通知は **adapter→core の継ぎ目を跨ぐドメインイベント** としてモデル化する:

- backend port は **イベントストリーム**（中立なドメインイベント型の async stream）を公開する — 生の callback ではなくリアクティブに消費される、DDD の Domain Event。
- **流れ:** adapter が OS を観測し（accessibility / ウィンドウシステムの通知、workspace の起動 / 終了、…）、ノイズの多い framework 固有のシグナルを綺麗な中立イベントへ翻訳してストリームに流す; Controller がそれを消費して Core の状態を突き合わせる。core / controller が生の OS 通知を見ることは決してない。
- **observer のライフサイクルを隔離せよ** — 小さな再利用可能な契約（一貫した `init(onChange:)` / `start()` / `stop()` の形）の背後に置き、どの observer 型も同じやり方で挿さるようにする。

## アーキテクチャ上の関心事としての並行性

スレッディングは設計の第一級の次元であり、後付けの考慮事項ではない:

- **可変サブシステム 1 つにつき直列化の権限は 1 つ。** adapter の可変状態はすべて単一の serial queue に閉じ込め、*あらゆる* 変更 **と読み取り** をそこ経由にする（読み取りも writer に対して破れる）。これが `@unchecked Sendable` な adapter を健全にしているものだ — 状態への入り口すべてに precondition を置き、閉じ込めを実行時に強制せよ。
- **actor を跨ぐ辺を非巡回に保て。** `main → workQueue` は *常に async* にする; `workQueue → main` の *sync* は、main で走らなければならない framework 固定の読み取り（例: スクリーンの幾何）に限って許す。main が work queue でブロックすることが決してないので、辺は巡回を作らない — `main → workQueue` の sync がどこかにあれば、それが巡回を閉じてデッドロックする。
- **ドメインを跨ぐときは不変な値のスナップショットを渡し、共有可変状態は決して渡すな。** 状態は work queue 上で確定させ、その後 *値としての plan*（要素 + フレーム）を main に閉じたドライバへ 1 ホップで渡す; 2 つの時計が状態を共有することは決してない。
- **非 `Sendable` な UI 境界を明示せよ。** preset / スタイルのデータは純粋な `Sendable` 値のまま保つ（例: hex の `UInt32`）; 非 `Sendable` な framework オブジェクト（例: 色）を生む *解決済み* 側だけを `@MainActor` に制約する。framework オブジェクトを main actor の外で解決するな。

## 別の projection も純粋のままにする

同じドメイン状態を *projection* する 2 つ目の直交した方法（同じ entity 群に対する別のグルーピング / レンズ）を足すときも、線を守れ:

- **projection と変更計画の面をまるごと純粋な Core に置け** — `project(...)` 関数と `resolve(...) → Plan` 関数 — そうすれば網羅的にユニットテストでき、view は描画専用のままでいられる。
- **config と result は別の型に保て** — *宣言された* config（ユーザーが求めたもの）と *計算された* 描画可能物（実際に描画したもの）。混同するな。
- **新しいモードは正確に縮退させよ** — 未設定なら旧来の既定へバイト単位で同一に畳み、明示的な `isActive` 述語で門を作る。
- **変更は純粋な resolver を通せ** — 意図を実行可能な `Plan` に変え、中核の不変条件を検証し、不変条件が保てないときは **不活性な plan**（no-op / スナップバック）を返す; 不純な controller は不活性でない plan だけを発行する。
- **計算は 1 回、描画は N 回** — すべての view が順序付き・計算済みの単一リストを消費するので、複数 view のハイライト / 選択ロジックはどのサーフェスでも同一になる。

## スコープの規律: 非目標もアーキテクチャ

アーキテクチャとは、作ることを拒んだものでもある:

- **能力の硬い境界を最初に名指し、守り抜け**（sandbox、entitlement、SIP 有効、公開 API のみ、injection 無し）。「この機能は境界の外へ出ることを我々に強いるか?」を門の質問にせよ — 境界を跨ぐ機能は別の fork になるのであって、後付けの継ぎ足しにはならない。これが core を小さく、信頼モデルを無傷に保つ。
- **外部ツールの関心事を吸収するのではなく、外部ツールと合成せよ**（ショートカット、ルールエンジン、永続化は外へ委譲）。
- **明示的に設計へ入れていない限り、実行時状態は永続化しない** — config は読み取り専用のテンプレート; 実行時の上書きはセッション限り。

## アーキテクチャを守る横断的な規約

- **診断も依存規則に従う** — ロギングのユーティリティを Core に置き、どのレイヤーもレイヤー境界を跨がずに呼べるようにする。
- **対称で、パターンに基づく面** — UI サーフェスの追加は、新しいエントリ 1 つとそれに対応する dispatch の case だけで済むはず; view ごとの特注フラグを再導入するな。「Core/Adapter を触らずに view を足せる」という約束は CLI 側にも映されるべきだ。
- **正規化の継ぎ目は 1 つ** — 未知の入力や範囲外の入力は拒否せず既定へ clamp / 正規化する。それを `effective*` アクセサの背後に置き、それを *唯一* 認められた読み取り経路とする。生の optional フィールドを直接読むな。
- **根拠は repo 内に置け** — 対応表、glossary、参考文献リスト（広い→狭い、言語中立→言語固有の順）を置き、repo を冷えた状態で開き直す担当者を経ても意図とユビキタス言語が生き残るようにする。

## 要約チェックリスト

1. 3 レイヤー — Core（純粋）/ Adapter（それぞれ backend の軸 1 つ）/ View（GUI 専用）。レイヤーを跨ぐ ⇒ port の欠落。
2. すべては内側の Core の protocol を向く; backend の型は adapter の外へ決して出ない; 継ぎ目で変換する。
3. View レイヤーの既定は最上位の UI ツールキット（SwiftUI）; 下位のもの（AppKit）は名前を与えた少数の必須 floor に封じ込める — 広げる前に検証し、正本リストはプロジェクトの正典に置く。
4. 実装が 1 つでも port は残す — それがテストの継ぎ目。
5. port は backend の軸で分割する; framework 中立に保つ（包装は view で）。
6. 変わりうる外部契約（文法、ワイヤフォーマット、スナップショット）は、純粋な translator を伴う port として扱う。
7. use case と view model のレイヤーは YAGNI で先送り; トリガーを正確に記録; 発火するまで凍結。
8. コードの配置はテスト可能性で決める; 値型は最初の利用者と一緒に出す。
9. OS の通知は adapter→core を跨ぐ中立なドメインイベントストリームとしてモデル化する。
10. 可変サブシステム 1 つにつき直列化の権限は 1 つ、アクセスはすべてそこ経由、実行時に強制、actor を跨ぐ辺は非巡回; ドメイン跨ぎは値のスナップショットで。
11. 別の projection も純粋のまま（`project`, `resolve→Plan`）、正確に縮退させ、述語で門を作る; view は計算済みの結果を描画するだけ。
12. 能力の硬い境界を名指して守る; 境界外の機能は fork であって、選択肢ではない。
13. Clean-Arch/DDD の対応表 + glossary を保ち、意図と言語が冷えた再オープンを生き延びるようにする。
