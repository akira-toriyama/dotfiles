# claude-md-eval

CLAUDE.md の変更を、配る前に測るハーネス。

散文で挙動を変えるもの —— `chezmoi/private_dot_claude/CLAUDE.md` の節、`skills/*/SKILL.md`
—— は、読んだだけでは効くか分からない。実例: 出力の形の節を初めて書いた時、自信を持って
選んだ 8 規則のうち 2 つが不良品だった（1 つは空振り、1 つは有害）。読んで気づけたものは
ゼロで、止めたのはこのハーネス。

## 使い方

測りたい節だけを書いた Markdown を用意して、2 コマンド。

```sh
python3 run.py   --candidate /path/to/section.md
python3 judge.py
```

`run.py` が baseline（節なし）と candidate（節あり）の応答を作り、`judge.py` が盲検で
判定してリリースゲートを適用する。ゲートが通れば exit 0、落ちれば **exit 3**
（argparse の usage エラー = exit 2 と区別するため。以前は両方 2 だった）。

既定は 16 ケース × 2 試行 × 2 条件 = 応答 64 本、判定 32 ペア。実測で 10 分・$6 前後。
中断しても `results/responses.jsonl` を見て再開する（完了済みの行は作り直さない）。

```sh
python3 run.py --candidate sec.md --trials 3 --model claude-opus-5
python3 judge.py --responses results/responses.jsonl --out results/verdicts.json
python3 -m unittest test_eval          # ハーネス自身のテスト
```

### 2 版を比べる（`--baseline`）

`--baseline` を渡すと baseline 腕にも別のファイルが載る。既定の「節なし vs 節あり」が
**足すか足さないか**しか測れないのに対し、こちらは**版 A vs 版 B** を測る。

```sh
git show <old-sha>:chezmoi/private_dot_claude/CLAUDE.md > /tmp/old.md
python3 run.py --baseline /tmp/old.md --candidate chezmoi/private_dot_claude/CLAUDE.md \
               --out results/reorder.jsonl
python3 judge.py --responses results/reorder.jsonl --out results/reorder-verdicts.json
```

これが要るのは、**内容を足しも引きもしない編集**（節の並べ替え・1 bullet の分割・
precedence の明示）が既定の腕構成ではコントラストを作れないため。それらは
「測る必要が無い」のではなく **「測れなかった」**（PR #274 の構造再編がこれで、
測らずに merge された）。

全文 2 本を system prompt に載せるので、節だけの比較よりトークンは増える。

**同じ `--out` を腕違いで使い回すと exit 3 で止まる。** 各行に `arms_key`
（model + 両腕の本文の hash）が入っていて、別の比較の行が混ざったファイルへの追記を
拒否する。`judge.py` は `(case_id, trial)` でペアにするだけで腕を見ないので、
混ざると「誰も実行していない比較」の判定が出てしまう。

## 何を測っているか

**客観指標**（モデルを通さない）: 文字数・行数・箇条書き数・見出し数・1 行目の長さ、
そして定型句の出現数を 2 バケツで数える。

- `named_filler` = その節が名指しで禁止した語
- `unnamed_filler` = 節が名指ししていない前置き・締めのパターン

named だけ減って unnamed が減らないなら、その規則は**文字列を止めているだけでパターンを
止めていない**。両方動かないなら、その規則は**空振り**（禁止した語を baseline が最初から
使っていない）。実際に 1 つ目の草案で後者が起きた。

**定型発火**（`fire_regex` を持つケースのみ）: 応答がそのケースの regex に一致した数を
条件別に数える。**regex は否定を読めない**ので、「その語を推奨した」ではなく「その語に触れた」
しか数えられない —— 規則が当たらないことを*説明する*正しい応答も、その語を書けば発火する
（2026-07-28 に `triage-fix-now` で踏んだ: 節が即修正閾値を飲み込んだと読める 2/3 発火は、
実際には全試行が「その場で直す・起票しない」と正答した上での言及だった）。**fire 数だけで
結論を書かず、必ず `results/*.jsonl` の応答本文を読むこと。**「作業・task 依頼への返し方」節のように**効果が定型句の出現そのもの**である
規則は、汎用の A/B 判定では測れないため。ゲートには入れない —— work-close 系ケースでの
発火は節が効いている証拠、consult 系ケースでの発火は誤発火（節の害）で、どちらかは
ケースの意図が決める。regex がプロンプト自身に含まれていないことは `test_eval.py` が検査する
（含まれると、どちらの腕もオウム返しで発火でき、節でなくプロンプトを測ることになる）。

## リリースゲート

`judge.gate()` が次のどれかに当たると BLOCKED を返す。

1. 判定に失敗したペアがある
2. candidate の勝ち数が baseline 以下
3. **「必要な内容を削って」勝ったペアが多すぎる** —— 判定基準は腕構成で変わる（下記）

3 が肝。勝ち数だけ見ると、中身を削って読みやすくしただけの節が通ってしまう。負けた側に
あった指摘を勝った側が落としているかを判定者に別途聞いて、その率で止める。

### 削り判定は腕構成で切り替わる（`baseline_mode`）

| 腕構成 | 行の `baseline_mode` | 削り判定 | 既定 |
|---|---|---|---|
| 節なし vs 節あり | `none` | candidate の削り勝ちが**全判定ペアに占める絶対率** | `--cut-rate 0.25` |
| 版 A vs 版 B（`--baseline`） | `file` | candidate の削り勝ちが baseline のそれを**超えた分**（差） | `--cut-delta 0.10` |

**絶対率を 2 腕比較に転用できない**（実測で判明）。2 腕では**両方の腕が CLAUDE.md 全文を
積み**、その CLAUDE.md 自身が「スクロールなしで読める長さ」を要求するので、削りは節の害では
なく**両腕共通の入力の効果**になる。実測 1 回（PR #274 の旧版 vs 新版・30 ペア）で
baseline 8 / candidate 11 の削り勝ちとなり、絶対率 25% は「置き換え前より悪くない candidate」
を BLOCKED にした。差で見るのはこのため。

**`--cut-delta` の 0.10 は暫定値**。較正スイープでなく上記 n=1 の観測から置いただけなので、
値を動かす時は測ってから決める（フラグにしてあるのは、関数を触らずに差し替えられるように
するため）。

判定モードは `judge.py` が `responses.jsonl` の `baseline_mode` から自動で決める。この
フィールドが**無い**行（実装前に書かれた行）は、黙って片腕モードに落とすと 2 腕の run を
静かに誤判定するので、警告を出す。

## 隔離（壊すと測定が無意味になる）

- `--setting-sources ""` —— これが無いと、operator 自身の CLAUDE.md・plugin・hook が
  **baseline にも**入り、節を節自身と比較することになる。`test_eval.py` が両条件について
  この引数を検査している。
- `--system-prompt` で既定のシステムプロンプトを置き換える。`--tools ""` はツールを消すが
  「ツールを持つエージェント」という枠組みは残るので、モデルが実行されないツール呼び出しを
  **文字列として書き**、応答が壊れた断片になる。最初の測定はこれで 12 ケース中 8 件が汚染された。
- `--model` は明示 pin。日常運用の `opus[1m]` alias（常に最新に乗る）とは目的が違い、
  ここは再現性が優先。**pin したモデルは結果の一部**なので、数値を残す時は一緒に記録する。

## 踏んだ罠

- `--tools` は可変長引数。`--tools "" <prompt>` と書くとプロンプトまで飲み込んで
  「入力が無い」で落ちる。後続にフラグがある条件だけ成功して**片方の腕だけ壊れる**ので
  気づきにくい。プロンプトは stdin で渡すこと。

## 測れないこと

headless の単発応答の形だけ。対話の複数ターンにわたる挙動、ツールを使う実作業中の振る舞い、
長いセッションでの遵守率は範囲外。判定者も LLM なので絶対ではない。

**skill の description が発火するかは測れない。** 隔離のために `--setting-sources ""` と
`--tools ""` を渡している以上、そのセッションには Skill ツール自体が存在しない。
description を書き換えて「呼ばれやすくなったか」を見るには、ツールを持つ実セッションが
要る＝このハーネスの外。

work-close 系ケース（W1/W2）はこの制約の中での近似 —— 「作業を終えた状況」をプロンプトに
書き込んだ単発応答で定型の発火を測る。実セッション末尾（長い文脈の後）での発火率は
これでは測れない。定型使用時の整形（task ID / なし）は Stop hook
`claude-work-report-check` が live で強制するので、ここでは発火だけを見る。
